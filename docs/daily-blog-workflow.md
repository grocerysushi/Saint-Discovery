## Daily files

Create `research/blog-daily/YYYY-MM-DD-0500/` with:

- `plan.json`: `date`, `timeZone: "America/Chicago"`, `time: "05:00"`, a nonempty `authorId`, and `topicAliases` (alternative names/titles for the proposed subject).
- `content.json`: precisely the existing BlogContent fields: `title`, `slug`, `excerpt`, `author`, `category`, `cover`, `coverAlt`, `coverCredit`, `ads: false`, and Tiptap `body`. No inline image nodes, even repeated covers. Cover fields are replaced from optimized metadata during preparation.
- `research.json`: `sources`, each with `url`, `title`, `claims` (specific claims supported), and `authoritativeCatholic: true` for at least one authoritative Catholic source. At least two sources are required. Each source must be linked in the article body. Read them; a 200 status alone is not evidence.
- `research.json` also includes `artwork`: `status` (`public-domain` or `licensed`), `sourceUrl`, `rightsUrl`, `artist`, `title`, `license`, `rightsEvidence`, `attribution`, and `actualArtwork: true`. Credit must equal `metadata.json.coverCredit` and sourceUrl must equal its `cover`.
- `metadata.json`: original artwork URL in `cover`, accurate `coverAlt`, complete `coverCredit`. Preserve the reviewed original artwork locally.
- `catalog.json`: a complete snapshot of both draft and published titles/slugs, generated by the read-only snapshot command below. Do not substitute only the public journal. Trashed records are included conservatively.

Do not copy test fixtures into a real day. They deliberately contain fictitious evidence and cannot pass the live cover gate.

## Research, prepare, review, publish

1. Verify the linked project and take a fresh read-only snapshot:
   `node scripts/prepare-daily-blog.mjs research/blog-daily/YYYY-MM-DD-0500 --snapshot`
2. Research a genuinely new Catholic subject against the complete catalog. Prioritize Vatican/USCCB sources and reviewed Catholic scholarship. Distinguish historical uncertainty and tradition from established facts. Use current liturgical calendar evidence where relevant; do not promote blesseds, Orthodox-only figures, observances or unresolved identities as canonized Catholic saints. Write accessible original prose with useful citations, not fabricated quotations.
3. Find actual public-domain or appropriately licensed artwork. Verify the individual object's rights, not merely the hosting site's reputation. Save the original and provenance. Follow `docs/blog-image-publishing.md` and the existing optimizer. An upload requires existing user authorization. Run without `--upload` first if publication/upload is not authorized. Inspect all variants; do not crop or enlarge.
4. Once authorized and verified upload receipts exist, run:
   `node scripts/prepare-daily-blog.mjs research/blog-daily/YYYY-MM-DD-0500`
   This writes matching `post.json`, guarded `publish.sql`, hashes, and an **unapproved** editorial-review template. It never publishes or uploads.
5. A separate editorial reviewer reads the complete files, actual source pages and catalog, inspects the original and optimized artwork, and verifies Catholic accuracy, source support, semantic topic distinctness, rights/attribution, alt text, no inline images and ad-free content. They copy `editorial-review.template.json` to `editorial-review.json`, set their own distinct `reviewerId`, `reviewedAt` ISO timestamp, `status: "approved"`, all applicable check flags true, and substantive `notes`. Hashes must be computed from the actual reviewed files. The reviewer must not approve without doing the review. Any edit requires regeneration and fresh independent review. Review expires after 24 hours.
6. Run only the mandatory entry point:
   `node scripts/publish-optimized-blog.mjs research/blog-daily/YYYY-MM-DD-0500`
   Never invoke an old per-day script, direct SQL, or the runtime module as a workaround. Existing ads, remote cover integrity, metadata, credit and exact SQL-payload checks remain mandatory. The reusable guard additionally verifies all review hashes, original artwork hash, matching draft/publication, existing application validation, date, links and an immediately refreshed catalog. Link redirects are checked against the explicit source-host allowlist; new source hosts require reviewed code changes, not silent acceptance. Broken/blocked links stop publication.
7. Inspect the live article **and journal** in a browser. Confirm correct text/citations, actual optimized cover and responsive siblings, full artwork, credits, useful alt text, no `/_next/image`, no ad scripts/units/placeholders, working links, and preserved analytics consent/classroom privacy. Save timestamped checks and screenshots in `live-verification.json`/the day's record. `published-live-verification-required` explicitly means this final check has not been done. Do not call the task complete until it is.

## Safety, retries and recovery

The publishing SQL takes write-excluding locks on both existing blog tables, then rechecks the Central clock, existing day, deterministic ID and title/slug conflicts before inserting both content stages atomically. There is no schema change. The complete reviewed catalog must remain unchanged before publishing; if it changes, refresh and re-review semantic topic originality. Normalized title/alias comparisons are only a backstop, not semantic deduplication.

The SQL and immediate recheck prevent competing guarded runs from inserting duplicates. They cannot permanently stop a manual editor or unrelated tool from publishing another post later; globally enforcing that policy would require a separately approved database change. No such migration is included.

A local `.publishing-lock` prevents overlapping runs in the same day directory. A crashed process can leave this directory. Do not automatically delete it. Check that no publisher is running and reconcile the database first.

After a timeout or uncertain result, do not create a new UUID, change the day, or run raw SQL. Use the read-only command, which also works on later days:

`node scripts/check-daily-blog-status.mjs research/blog-daily/YYYY-MM-DD-0500`

`published-matching` means exactly the expected two stages, date and content exist. `not-found` is only a read result; confirm no attempt remains active before rerunning the mandatory wrapper in today's permitted window. Any difference is a blocker for manual reconciliation. An identical completed retry never updates the original post. Missing auth, unavailable storage, rights doubts, stale review, changed catalog, unsupported SQL, denied actions, network failures, unknown outcomes or a wrong project all stop the run. Do not weaken validation to meet the schedule.

## Read-only deployment preflight
